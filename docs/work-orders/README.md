# 工作单协议（所有执行会话必读）

## 角色

- **架构会话（本目录 docs/ 的维护方）**：冻结契约、排期、仲裁、下发指令、验收把关。不直接写业务代码；**禁止调用、模拟或代替任何执行会话完成工单**。执行会话未交付时，架构会话只能补充/修订工单或退回，不能代做。
- **执行会话**：部署 / 数据 / 后端 / 前端 / 测试。由用户分别开启；架构会话下发工单与启动说明，执行会话各自领工单干活。

## 执行规则

1. **开工前先读**：本协议 → 自己工单的「总览」→ `docs/arch/` 全部四份基线 → 需求基线 V2.0（仓库根目录）中自己模块的章节。架构基线与需求基线冲突时以架构基线为准；架构基线未覆盖处以需求基线为准。
2. **冻结文件**：`docs/arch/*` 对本会话只读。认为需要变更 → 在 `docs/STATUS.md`「偏差与仲裁」登记并停止相关部分，等架构会话裁定；其余部分继续。
3. **禁止事项**（触碰即返工，详见 arch/00 §3.13 与需求基线 §19）：Toast 冒充成功、硬编码统计、本地状态当数据库、隐藏按钮代替服务端鉴权、浮点金额/浮点工时、前端提交可信合计、范围蔓延。
4. **目录边界**：只动自己工单声明的文件/目录。`package.json` 依赖只改自己 workspace 的；根级文件（根 package.json、docker-compose.yml、.env.example）归部署会话。
5. **完成动作**：跑通工单验收命令 → 更新 `docs/STATUS.md` 自己那一行状态为「待验收」+ 在「交接记录」写一段：做了什么、怎么验证、留了什么坑 → 通知架构会话验收。
6. **测试会话验收不通过** → 工单打回，状态改回「进行中」，打回原因写「交接记录」。

## 状态机

工单状态：`未认领 → 进行中 → 待验收 → 通过 / 打回(→进行中)`。认领时把自己会话名和日期写进 STATUS.md。

## 提交约定

- git 提交信息前缀：`[部署]/[数据]/[后端]/[前端]/[测试]/[架构] 描述`。
- 每个工单完成至少一个 commit；不提交与工单无关的改动。

## 串行执行（2026-10-26 调整；2026-11-13 强化）

同一项目目录下会话只能串行：任何时刻只有一个工单「进行中」，由架构会话按依赖顺序逐一解锁，不存在并发改文件冲突。仍须遵守目录边界；`shared/` 只增不改（改需架构会话）；数据库迁移按时间序追加，禁止改已提交迁移。

**调度硬规则：** 架构会话一次只下发一个可执行工单；下发后等待用户在新的对应执行会话中开工，不能在本会话内直接实现、调起实现代理或同时派发多个执行工单。上一工单经架构验收「通过」后，才允许把下一工单改为「未认领/已解锁」并下发启动指令。
