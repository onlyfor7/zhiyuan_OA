# 架构基线 03 · 权限与审批模型

**裁定方：** 架构会话　**依据：** 需求基线 V2.0 §3/§6.2/§11　**状态：** 已冻结（迭代 0 期间）
**核心原则：** 权限判断全部在服务端执行且各入口同口径；前端只做呈现适配。财务/管理员等高角色**不自动获得**法律业务内容权限（基线 §19.8）。

---

## 1. 角色目录（`roles.key` 冻结）

| key | 名称 | 要点 |
|---|---|---|
| `partner` | 管理层/合伙人 | 项目组合监督、重大审批；按管辖项目范围 |
| `project_manager` | 项目负责人 | 项目内全权（受职责分离约束） |
| `member` | 项目成员 | 本人业务创建、项目内按授权查看 |
| `quality_lead` | 质量负责人 | 质量工作流 + 涉质量决策参与 |
| `finance` | 财务/经费管理员 | 预算/经费/费用/支付处理；**不含**法律文件内容 |
| `archivist` | 档案管理员 | 归档、完整性、授权管理 |
| `sysadmin` | 权限/系统管理员 | 组织、角色、参数配置；**不默认读取**业务内容与财务附件 |
| `viewer` | 只读查阅人 | 仅经 AccessGrant 的限定范围与期限；默认不见经费/费用/工时明细 |

## 2. 判定模型：RBAC + ABAC 合成

一次请求的权限判定按序合成，全部通过才放行：

1. **全局角色（RBAC）**：`user_roles` 决定能力集（能做什么动作）。
2. **项目上下文（ABAC）**：`project_members` 的项目内角色决定**在哪个项目**能做；非成员默认无项目任何权限。
3. **密级（ABAC）**：对象 `confidentiality_level` ≤ 用户/项目授权密级。
4. **信息墙（ABAC）**：`access_grants` 负向/正向名单或项目隔离配置（迭代 1 落地信息墙表，迭代 0 预留判定钩子）。
5. **临时授权（ABAC）**：有效 `access_grants`（active 且未到期）可授予限定动作（只读/下载）；到期与撤销即时失效。
6. **职责分离（规则）**：见 §4，作为审批策略的强制校验，不能被角色覆盖。

实现：service 层调用统一 `access.can(ctx.user, action, resource)`；列表查询用 SQL 级过滤（join project_members / access_grants），**禁止查出后内存过滤**（会破坏分页与计数口径）。

## 4. 职责分离强制规则（服务端校验，不可配置关闭）

1. 出差/经费/费用申请人不得批准本人申请（`SELF_APPROVAL_BLOCKED`）。
2. 项目负责人本人工时由指定管理层/代理人审批，不得自审。
3. 财务角色获得财务处理权，不因此获得法律业务文件内容权。
4. 会议参与人 ≠ 项目成员，不自动获得项目访问权。
5. sysadmin 可配置权限，不因此获得项目内容、票据、工时明细读取权。

## 5. 无泄露响应策略

- 列表/搜索/统计/驾驶舱：无权限对象**静默排除**（SQL 过滤），总数、页签计数也不含。
- 详情/直链/下载：统一返回 `ACCESS_DENIED_OR_GONE`（NOT_FOUND 形态），与「不存在」不可区分。
- 错误信息、枚举值、编号序列不得泄露客户名/项目全称等敏感内容。

## 6. 审批引擎（公共能力，迭代 1 交付，此处冻结设计）

**禁止各模块自建审批逻辑**（基线 §6.2）。唯一实现位于 `server/src/services/approval/`。

### 数据（迭代 1 建表，语义冻结）

- `approval_instances`：id, biz_type, biz_id, applicant_id, form_snapshot jsonb, policy_snapshot jsonb, current_step_seq, status(pending/approved/rejected/withdrawn), idempotency_key (unique), submitted_at, completed_at。
- `approval_steps`：instance_id, seq, approver_id 或 approver_role, countersign(any/all), action(pending/approved/rejected/transferred), comment, acted_at, delegated_from。
- `approval_policies`：biz_type, match_json（金额阈值/密级/超预算/项目类型）, steps_json（有序步骤定义）, enabled。

### 流程铁律

1. 提交时冻结 `form_snapshot` + `policy_snapshot`；审批期间改关键字段必须撤回重提。
2. 审批动作服务端重新鉴权；申请人/审批人/代理人身份以 session 与策略解析为准，**前端传入不直接信任**。
3. 终审通过与业务写入、台账、通知、审计在**同一事务**；失败整体回滚，界面不得假成功。
4. 驳回必填理由；通过后原申请只读，只能变更/调整/新版本。
5. 幂等：重复提交、网络重试、并发审批不产双结果（幂等键 + 步骤状态条件更新）。
6. 支持：草稿、提交、撤回、通过、驳回、转交、代理、会签（步骤内 any/all）。
7. 阈值默认值进 `system_config` 种子（如经费 ≥ 50,000 元升管理层）；**可配置，不写死**。

### 与业务模块的集成协议

业务模块只调用 `approvalEngine.submit(bizType, bizId, formSnapshot)` 与接收回调 `onApprovalResult(bizId, result)`（同事务内执行自身状态迁移与台账）。模块不直接写 approval 表。

## 7. AccessGrant 生命周期（档案授权，迭代 1 落地）

`pending_approval → active → expired/revoked`；到期由查询时判定 + 定时任务兜底双保险；撤销/到期即时生效，不默认续期；授权、撤权、到期命中均审计。直链下载必须过 grant 校验 + 短期令牌（arch/00 §5）。
