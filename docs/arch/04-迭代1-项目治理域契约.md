## 2. 数据模型细案（18 张新表 + 2 处存量加列）

通用字段（id/code/审计四件套/row_version）按 arch/01 §2。**新增编号前缀**（注册表 v1.2，数据会话补入 `shared/constants.ts`）：`CHG` 延期申请、`STG` 阶段、`MLS` 里程碑、`DLV` 交付物。

### 2.1 存量表加列（追加式迁移，禁止改已提交迁移）

| 表 | 加列 | 说明 |
|---|---|---|
| `file_objects` | `source_type text null`、`source_id uuid null` | 落地迭代 0 已接收但未持久化的来源；新上传必填。迭代 0 遗留行允许为 null |
| `file_versions` | `idempotency_key text null unique` | D2 裁定落地：upload 契约增补可选幂等键 |

### 2.2 项目结构

- `stages`：project_id, code(STG), name, seq int, planned_start/end date, actual_start/end date null, status `stage_status`, 四件套+row_version。
- `milestones`：project_id, stage_id null, code(MLS), name, seq, planned_date date, actual_date null, status `milestone_status`, 四件套+row_version。
- `tasks`：project_id, stage_id null, milestone_id null, code(TSK), title, description null, assignee_id null, planned_start/end date, actual_start/end timestamptz null, status `task_status` default pending, source_type/source_id null（恢复措施/决策执行/后续行动项的来源）, completed_at null, 四件套+row_version。
- `deliverables`：project_id, milestone_id null, task_id null, code(DLV), name, required bool default true, status `deliverable_status`(pending/delivered/accepted), file_version_id FK null, delivered_at/by null, 四件套+row_version。

### 2.3 计划版本（PLN 核心）

- `plan_versions`：project_id, version_no int, kind `plan_version_kind`(baseline/change), status `plan_version_status`(active/superseded), source_change_request_id FK null, notes null, 四件套。`unique(project_id, version_no)`；**每项目恰一个 active**（部分唯一索引 `where status='active'`）。
- `plan_items`：plan_version_id FK, item_type `plan_item_type`(stage/milestone/task), ref_id uuid, **name text not null（v1.1，2026-10-27 增补：版本时点快照名，改名不改历史版本显示；存量行由迁移回填）**, planned_start date, planned_end date, seq int, depends_on uuid[] default '{}'（同版本 plan_item id 集）, created 两件套。

**不变量 PLN-I1：** plan_items 一旦写入永不 UPDATE/DELETE；计划的「内容变更」只能产生新版本。live 表（stages/milestones/tasks）的 planned_* 承载当前计划，**没有任何 API 可直接改 planned_***——只能由延期申请通过时在同一事务内（① 插新版本及 items ② 更新 live planned_* ③ 旧版本 superseded ④ 审计+通知）原子完成。甘特三轨：基线=v1 items，当前=active 版本 items（=live），实际=live actual_*。

### 2.4 延期申请（CHG）

- `change_requests`：project_id, code(CHG), title, target_items jsonb `[{ref_id, item_type, original_start, original_end, new_start, new_end}]`, reason text, impact text, recovery_measures jsonb `[{measure, owner_id, checkpoint_date}]`, level `change_level`(normal/key), status `change_request_status`, approval_instance_id FK null, resulting_plan_version_id FK null, submitted_at null, decided_at null, 四件套+row_version。
- 提交校验（服务端）：reason/impact/recovery_measures 非空；target_items 的原日期必须与当前计划一致（防篡改）。key 级走管理层审批（策略种子）。通过后同事务：生成 plan_version(v(n+1), kind=change) + 更新 live planned_* + 恢复措施生成 tasks(source_type='change_request') + 通知责任人。

### 2.5 质量（QLT）

- `quality_issues`：project_id, code(QLT), title, description, severity `quality_severity`(critical/severe/major/minor), status `quality_issue_status`, reporter_id, handler_id null, reviewer_id null, root_cause null, source_type/source_id null, is_blocking bool（= severity∈(critical,severe) 且 status≠closed，写入时维护）, closed_at null, 四件套+row_version。
- `quality_issue_events`（只追加）：issue_id FK, actor_id, action `quality_event_action`(create/assign/handle_submit/review_pass/review_return/reopen), note null, created_at。处理与复核历史以此为准。
- `quality_check_items`：project_id, stage_id null, name, required bool default true, status `check_item_status`(pending/passed/failed/waived), checked_by/at null, 四件套。项目创建时由模板生成。
- 硬规则：severe/critical 的处理人与复核人**必须不同人**（服务端强制，`SELF_REVIEW_BLOCKED`）；critical/severe 未关闭 → is_blocking=true → 阻断结项检查与质量门禁。

### 2.6 决策（DEC）

- `decisions`：project_id, code(DEC), title, context text, source_type/source_id null, options jsonb `[{key: delay/add_staff/scope_reduce/phased_delivery/risk_accept/other, summary, impact, risk}]`, pm_opinion text null, quality_opinion text null, final_option null, final_reason null, conditions null, checkpoints jsonb null `[{point, date, owner_id}]`, status `decision_status`(draft/deciding/decided/verified), decider_id null, decided_at null, verification_note null, verified_at/by null, 四件套+row_version。
- 硬规则：decide 时 final_option/final_reason/conditions/checkpoints 必填且双意见齐备；checkpoints 生成 tasks(source_type='decision')；verify 必须 decided 之后。

### 2.7 周报（ARH）

- `weekly_reports`：project_id, code(RPT), period_start/end date, version_no int default 1, status `weekly_report_status`(draft/confirmed/archived), content jsonb（分节：progress/tasks/quality/decisions/risks/next_week）, confirmed_by/at null, archived_at null, 四件套+row_version。`unique(project_id, period_start, version_no)`。
- 规则：generateDraft 从真实来源聚合（本周完成任务/质量事件/决策/延期）；confirm → 固定版本；已确认后再改 = 同期间 version_no+1 新 draft，旧版本不动；archived 只读（`ARCHIVED_READONLY`）。归档时在 archive_links 登记（source_type='report'，目录 06）。

### 2.8 档案（DOC/SHR）

- `archive_directories`：project_id, dir_key, name, seq, unique(project_id, dir_key)。项目创建时按 §12.1 十一个目录种子生成。
- `archive_links`：project_id, directory_id FK, file_version_id FK null, source_type, source_id, business_date date, note null, created_by/at。**二态**：文件链接（file_version_id 非空 + 来源对）或报告链接（file_version_id 空 + source_type='report'）；check 约束强制二态。`unique(directory_id, file_version_id)`（部分索引）+ `unique(directory_id, source_type, source_id)`——同一入口不重复归集。

### 2.9 审批引擎（三表，唯一审批实现）

- `approval_instances`：code(APR), biz_type text, biz_id uuid, project_id null, applicant_id FK, form_snapshot jsonb, policy_snapshot jsonb, current_step_seq int default 1, status `approval_instance_status`(pending/approved/rejected/withdrawn), idempotency_key text **unique not null**, submitted_at, completed_at null, 四件套+row_version。
- `approval_steps`：instance_id FK, seq int, approver_id FK null, approver_role text null, countersign `countersign_rule`(any/all) default any, status `approval_step_status`(pending/approved/rejected/transferred/skipped), acted_by null, comment null, acted_at null, delegated_from null, unique(instance_id, seq)。
- `approval_policies`：biz_type, priority int default 100, match_json jsonb（可含 level/confidentiality/min_amount_cents/over_budget/project_type）, steps_json jsonb `[{approver_role|approver_id, countersign?}]`, enabled bool default true, description, 四件套。
- 角色解析：`project_manager` → 该项目 manager_id；`partner`/`archivist` 等全局角色 → 该角色全部用户（countersign 规则控制）。解析结果落到 step.approver_id 具体人。
- 种子策略：change_request level=key → [partner]；level=normal → [project_manager]；access_grant → [archivist]。
- **自审拦截**：步骤解析出申请人本人 → 引擎自动跳过该审批人；若某步骤因此无人可审 → 抛 `SELF_APPROVAL_BLOCKED`（策略配置错误，显式失败而非静默通过）。

### 2.10 模板

- `project_templates`：name, description, structure_json jsonb，enabled bool default true, 四件套。种子 2 个：诉讼案件标准模板、常年法律顾问模板。档案目录固定十一项不随模板。**structure_json 键名冻结（v1.2，2026-10-27，camelCase 与实现一致）**：`{stages:[{seq,name,days?}], checkItems:[{name,required?,stageSeq?}], tasks:[{name,stageSeq,offsetDays?,durationDays?,assigneeRole?}]}`；创建时 tasks 落入对应阶段区间生成真实任务（planned_start=阶段开始+offsetDays，默认 0；planned_end=+durationDays，默认 7；status=pending；assigneeRole 解析为成员或留空未分配），并同步写入 v1 plan_items（item_type='task'）。

### 2.11 pgEnum 新增清单（数据会话建）

`stage_status(pending/active/done)`、`milestone_status(pending/reached/missed)`、`task_status(pending/in_progress/done/cancelled)`、`deliverable_status(pending/delivered/accepted)`、`plan_version_kind(baseline/change)`、`plan_version_status(active/superseded)`、`plan_item_type(stage/milestone/task)`、`change_level(normal/key)`、`change_request_status(draft/pending_approval/approved/rejected/withdrawn)`、`quality_severity(critical/severe/major/minor)`、`quality_issue_status(open/handling/pending_review/closed)`、`quality_event_action(...)`、`check_item_status(pending/passed/failed/waived)`、`decision_status(draft/deciding/decided/verified)`、`weekly_report_status(draft/confirmed/archived)`、`approval_instance_status(pending/approved/rejected/withdrawn)`、`approval_step_status(pending/approved/rejected/transferred/skipped)`、`countersign_rule(any/all)`。

`shared` 增补（数据会话）：上述全部枚举常量；`errors.ts` 增补 `SELF_REVIEW_BLOCKED`、`POLICY_NOT_FOUND`；`NOTIFICATION_EVENT_TYPE` 增补 `approval_pending / approval_result / task_due_soon / task_overdue / quality_returned / decision_required / report_draft_ready`（§6）。

## 3. 状态机补充（冻结，与 arch/01 §3 同效力）

| 对象 | 迁移 | 硬限制 |
|---|---|---|
| task | pending → in_progress → done；pending/in_progress → cancelled | done/cancelled 终态；done 才可 reopen→pending（留痕） |
| milestone | pending → reached / missed | 记录 actual_date |
| stage | pending → active → done | 有未完成任务时 done 仅警告不阻断 |
| plan_version | active → superseded | 无回退；items 不可变 |
| change_request | draft → pending_approval → approved/rejected；pending → draft（撤回） | approved 终态不可逆；结果版本可追溯 |
| quality_issue | open → handling → pending_review → closed；pending_review → handling（退回）；closed → handling（重开） | severe+ 处理人≠复核人；退回必须 note |
| decision | draft → deciding → decided → verified | decide 必填四件+双意见；verified 需验证说明 |
| weekly_report | draft → confirmed → archived | confirmed 后修改=新版本；archived 只读 |
| approval_instance | pending → approved/rejected/withdrawn | 单一终态（条件更新防并发双终态） |

## 4. 审批引擎接口冻结（`server/src/services/approval/engine.ts`）

```ts
submit(tx, { bizType, bizId, projectId, applicantId, formSnapshot, idempotencyKey })
  // 策略解析（biz_type+enabled 按 priority，match_json 全部命中即中）；无命中 → POLICY_NOT_FOUND
  // 同事务建 instance+steps（角色解析为具体人）、冻结双快照；idempotencyKey 冲突→返回原实例
  // 自审跳过规则按 §2.9；返回 instance
act(tx, { instanceId, stepSeq, actorId, action: 'approve'|'reject'|'transfer', comment?, transferTo? })
  // 校验：实例 pending 且 current_step_seq=stepSeq；actor 是该步审批人或其代理
  // reject 必须 comment；条件 UPDATE steps set … where status='pending'（并发/重试安全，影响行数=0 视为已处理，直接返回现状）
  // approve 且还有后续步骤 → current_step_seq++；终审通过 → 同事务调用该 bizType 注册处理器（业务状态迁移+台账/通知/审计）
withdraw(tx, { instanceId, actorId })  // 仅申请人、仅 pending；同事务回调业务回 draft
registerHandler(bizType, { onApproved(tx, instance), onRejected(tx, instance), onWithdrawn(tx, instance) })
```

**会签语义（v1.1，2026-10-27 冻结）：** 同一步骤解析出多名审批人时，`countersign=all` 表示全员 approve 才推进，任一人 reject 即该步驳回（实现可将步骤展开为子序号行，行为语义不变）；`any` 表示一人生效。种子与并发测试覆盖随迭代 2 经费会签场景落地。

**模板阶段默认排期（v1.1）：** `structure_json` 的阶段可带 `days`；缺省按 14 天/段自项目开始日顺排，创建后调整走延期流程（PLN-I1）。

**act 幂等键语义（v1.2，2026-10-27 裁定，迭代 2 落地）：** `approval_steps` 增 `acted_idempotency_key text null`；同一步骤已被同一 key 处理 → 返回 200 + `{instance, applied:false}`（幂等成功语义，不报错）；终态实例上不同 key 的重放维持 409 `STATE_CONFLICT`。现状（迭代 1）：act 的条件更新+终态校验已保证单终态/无双写，key 字段闲置属已知形式差距，迭代 2 数据棒加列、后端棒消费并补用例。

迭代 1 接入审批引擎的对象：`change_request`、`access_grant`。质量复核与决策确认**不走**引擎（自有流程），延期与档案授权必须走引擎——禁止为它们单写审批逻辑。

## 5. API 契约清单（迭代 1 新增；形态与错误码沿用 arch/02）

| 域 | 过程 |

## 6. 通知与待办（迭代 1 启用写入）

| 事件 | 接收人 | 时机 |
|---|---|---|
| approval_pending | 当前步骤审批人 | 审批实例进入该步骤 |
| approval_result | 申请人 | 实例终态 |
| task_due_soon | 任务负责人 | 到期前 2 天（聚合键按日） |
| task_overdue | 任务负责人，逾期升级项目负责人 | 逾期当日；恢复措施类任务逾期直报 pm |
| quality_returned | 处理人 | 复核退回 |
| decision_required | 决策人（项目负责人/管理层） | 决策进入 deciding |
| report_draft_ready | 项目负责人 | 周起草生成 |
| grant_expiring | 被授权人+授权人 | 到期前 7 天 |

聚合：`aggregate_key = event_type + source_id + 日`，同键同日不重复建行。通知一律带 source_type/source_id 供前端直达处理页；处理后由业务动作同步 handled（不靠用户手动已读替代处理）。

## 7. 迭代 0 遗留落地（本迭代必须完成）

1. **D2**：upload 增补可选 `idempotencyKey`；`file_versions.idempotency_key` 唯一列；重复上传同键返回首次结果；测试会话翻转 probe 用例为拦截断言。
